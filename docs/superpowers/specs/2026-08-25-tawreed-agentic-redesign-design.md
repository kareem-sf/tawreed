# Tawreed Agentic Redesign

> **NOT YET IMPLEMENTED.** This document describes a planned future
> rearchitecture. The application currently shipping (`src/`, `engine/`,
> `src-tauri/`) does not implement the agent kernel, provider-bridge
> architecture, or bootstrapper described below — see `docs/ARCHITECTURE.md`
> for what actually exists today.

**Status:** Approved design

**Date:** 2026-08-25

**Product:** Tawreed
**Design path:** Architectural

## Executive summary

Tawreed will be redesigned as a local-first, cross-platform, agentic desktop
application dedicated to one job: turning one or more construction BOQs into
specialized, market-ready procurement packages without changing the source
commercial content.

The user interacts with one visible application artifact. On Windows that
artifact is `Tawreed.exe`. A native bootstrapper downloads, verifies, and
manages the application runtime under `~/.tawreed`. The application exposes a
minimal Adaptive Agent Workspace while a Tawreed-owned agent kernel coordinates
Codex, Claude, Gemini, and future AI provider bridges.

Tawreed has two related product capabilities:

1. **AI Package Architecture:** infer the project-specific procurement-package
   structure, assign every BOQ item to one owning package, resolve ambiguity
   with the engineer, and publish a project master workbook plus standalone
   package workbooks.
2. **AI Material Takeoff (MTO):** derive primary, constituent, ancillary, and
   consumable materials from BOQ work items; calculate net, waste, gross, and
   procurement quantities; and publish consolidated and package-level material
   requirements schedules.

AI owns interpretation, planning, routing, and self-review. Trusted tools own
source extraction, arithmetic, unit conversion, validation, file access, and
Excel publication. This keeps the product AI-driven without making source
truth or engineering calculations nondeterministic.

## Product contract

Tawreed is a **procurement-package preparation tool**. It is not a general
construction management platform.

### Primary user outcome

An engineer supplies one or more BOQs for a project. Tawreed understands the
items, creates a project-specific package architecture, resolves uncertainty,
and produces files the engineer can send directly to specialist suppliers or
subcontractors for pricing.

### Source-of-truth invariant

Source BOQ values are immutable. Tawreed must not alter item codes,
descriptions, units, quantities, rates, amounts, comments, or source
references. Derived outputs may omit confidential columns or add clearly
identified system metadata, but the original source ledger remains unchanged.

### Initial input scope

The first product scope accepts BOQ documents only. Specifications, drawings,
contracts, and general project folders are not used as supporting context in
the initial release.

Supported input families include:

- Excel workbooks: `.xls`, `.xlsx`, `.xlsm`, and `.xlsb`;
- PDFs, including searchable and scanned PDFs;
- images of BOQ pages: `.png`, `.jpg`, `.jpeg`, `.tif`, `.tiff`, `.webp`,
  and `.heic`;
- scanned documents requiring OCR; and
- multiple BOQ documents within the same project.

The ingestion architecture uses format adapters so CSV, ODS, and additional
document types can be added without changing the canonical item model.

### Outputs

Tawreed can produce:

- one project master workbook containing a cover, index, and one sheet per
  package;
- one standalone workbook per package containing a cover and the package's
  source items;
- internal and for-pricing variants when commercial data is present;
- one consolidated project Material Takeoff;
- one Material Takeoff per package;
- an assumption and decision report; and
- an audit trail and revision manifest.

The engineer chooses consolidated MTO, package-level MTO, or the complete set.
The complete set is the recommended default.

### Explicitly out of scope

The redesign does not include:

- editing the original BOQ;
- supplier or subcontractor relationship management;
- automatically emailing or distributing RFQs;
- bid comparison or tender adjudication;
- purchase orders;
- procurement scheduling, delivery tracking, or inventory management;
- contract authoring; or
- a required Tawreed cloud backend.

## Terminology

- **Source Document:** an immutable BOQ file supplied by the user.
- **Source Item:** one extracted BOQ item with exact source values and
  provenance.
- **Package:** a market-ready group of related work items intended for a
  specialist supplier or subcontractor.
- **Package Plan:** the project-specific set of packages generated by the AI.
- **Owning Package:** the single package to which a source item contributes its
  quantity and value.
- **Material Takeoff (MTO):** calculated quantities of materials required to
  execute BOQ work items.
- **Material Recipe:** a versioned decomposition and formula that maps a work
  item to constituent materials.
- **Gate:** an approval that the selected operating mode cannot bypass when the
  relevant risk is present.

## Operating modes

The UI presents professional outcome-oriented labels. Internal implementation
terms may remain in code but are not required user knowledge.

1. **Analysis and Recommendation:** Tawreed analyzes and recommends; the user
   approves actions before execution.
2. **Draft Preparation:** Tawreed creates a fully reversible draft and asks for
   approval before publication.
3. **Supervised Execution — recommended:** Tawreed proceeds autonomously and
   stops for material decisions and hard gates.
4. **Full Automation:** Tawreed completes the workflow without ordinary review,
   but still honors all hard gates.

Changing the operating mode changes approval frequency. It does not change the
engineering domain, tone, or product scope. There is no separate persona
system.

## System architecture

The selected architecture is a **Tawreed-Owned Agent Kernel**.

```text
Adaptive React Workspace
          |
Tauri / Rust Host
          |
Local Tawreed Agent Kernel
     |-- Codex SDK Bridge
     |-- Claude SDK Bridge
     |-- Gemini SDK Bridge
     `-- Future Provider Bridges
          |
Trusted Domain Tools
     |-- BOQ Ingestion and OCR
     |-- Source Traceability
     |-- Package Validation and Publication
     |-- MTO Calculation and Unit Conversion
     `-- Excel Publication
          |
Text-First Local Project Store
```

### Portable launcher

The user sees one launch artifact per platform:

- Windows: `Tawreed.exe`;
- macOS: a single visible `Tawreed.app`; and
- Linux: a single visible AppImage or equivalent desktop artifact.

Windows 10/11 x64 is the first release target. The architecture and project
format remain platform-neutral from the start, followed by macOS and Linux.

The visible artifact is a native bootstrapper and launcher. On first run it:

1. detects the platform and architecture;
2. creates `~/.tawreed`;
3. fetches a versioned compatibility manifest;
4. displays a single nontechnical "Preparing Tawreed for First Use" screen;
5. downloads required runtime packs into a staging directory;
6. verifies signatures, digests, sizes, and allowed extraction paths;
7. self-tests the runtime;
8. promotes the staged runtime atomically; and
9. starts the desktop application.

The user does not select Node.js, OCR, SDK, or provider-runtime components.
Dependency resolution is automatic. Lightweight provider bridges ship in the
agent runtime; heavyweight provider-specific executables can be downloaded
automatically when that connection is first configured.

### Release source and verification

Runtime packs are published as versioned GitHub Release assets, not read from a
repository branch. The repository should enable immutable releases and produce
release attestations. Every runtime manifest contains platform-specific URLs,
versions, sizes, SHA-256 digests, and signatures. The launcher's public
verification key is embedded in the launcher.

Downloads are resumable. A failed update leaves the previous version intact.
Verified updates download in the background, apply on the next launch, and
roll back automatically if startup health checks fail.

### Tauri / Rust host

Rust owns privileged and security-sensitive operations:

- runtime download and verification;
- path validation and safe archive extraction;
- atomic writes and revision publication;
- process lifecycle and sidecar permissions;
- constrained file and URL access;
- source hashing;
- project import and export; and
- update activation and rollback.

The browser-facing React layer never accesses provider APIs, credentials, or
arbitrary filesystem paths directly.

### Agent kernel

The agent kernel is a local, self-contained TypeScript/Node sidecar. It owns:

- task planning and decomposition;
- AI provider selection and routing;
- thread and session continuity;
- checkpoint creation;
- gate evaluation;
- project and global memory retrieval;
- tool orchestration;
- AI self-review; and
- provider failover preparation.

The kernel communicates with the Rust host through framed local JSON-RPC over
standard input/output or an equivalently private local transport. It does not
open a public network service.

### Provider bridges

Codex SDK is the first provider bridge. Claude and Gemini follow behind the
same Tawreed-owned contract. A provider bridge is not allowed to own the
product workflow or project data model.

Each bridge must implement the same conceptual operations:

```text
connect
health_check
start_or_resume_session
run_turn
stream_events
cancel_turn
normalize_usage
normalize_error
```

The router selects a provider using task capability, availability, quality,
latency, and configured cost preference. Advanced settings allow a manual
override. If the active provider fails, Tawreed can prepare a fallback, but it
must obtain consent before sharing project data with a provider that has not
previously received approval for that project.

### Trusted domain tools

The AI drives the workflow, but it calls deterministic tools for operations
where correctness must be reproducible:

- document decoding and OCR;
- row and table extraction;
- hashes and provenance;
- formula evaluation;
- unit conversion;
- waste and procurement rounding;
- duplicate and coverage checks;
- Excel generation; and
- atomic publication.

## Local storage

Tawreed uses a text-first local store under `~/.tawreed`.

```text
~/.tawreed/
|-- settings.json
|-- connections.json
|-- runtime-manifest.json
|-- runtime/
|   |-- launcher/
|   |-- app/
|   |-- agent-kernel/
|   `-- providers/
|-- assets/
|   |-- ocr/
|   `-- document-engine/
|-- rules/
|   `-- global.json
|-- projects/
|   `-- <project-id>/
|       |-- project.json
|       |-- sources/
|       |-- source-items.jsonl
|       |-- sessions.jsonl
|       |-- decisions.jsonl
|       |-- rules.json
|       |-- recipes.json
|       |-- assumptions.json
|       |-- audit.jsonl
|       |-- checkpoints/
|       `-- outputs/
|-- cache/
|-- staging/
`-- logs/
```

JSON stores bounded structured documents. JSONL stores append-oriented event
and item collections. Markdown may be used for user-readable generated
summaries. Source documents, Excel outputs, runtime binaries, OCR assets, and
temporary processing artifacts remain in their native binary formats.

### Plaintext connection data

Per the approved product constraint, Tawreed does not integrate Windows
Credential Manager or a Tawreed encryption layer. Tawreed-owned API keys and
tokens are stored as plaintext in `connections.json`.

The product must disclose this risk once when the first credential is saved.
Mitigations that do not change the plaintext requirement are mandatory:

- restrict file permissions to the current operating-system user;
- mask values in the UI;
- redact values from logs, diagnostics, and agent prompts;
- exclude credentials from project exports and backups;
- never commit or upload the file;
- provide one-click removal of one connection or all connections; and
- prevent provider responses from echoing secret values into audit events.

Provider-owned authentication files use provider-defined formats in a
provider-specific directory under `~/.tawreed` where the provider supports a
custom home directory. Tawreed does not add its own encryption layer or invoke
an operating-system credential manager. If a provider connection cannot run
without an operating-system credential store, that connection method is not
offered; Tawreed uses a compatible plaintext API-key or provider-home flow
instead.

### Project portability

Any project can be exported as `<ProjectName>.tawreed-project.zip`. The archive
contains source documents, project metadata, item ledger, approved rules,
recipes, assumptions, decisions, sessions, audit trail, and selected outputs.
It excludes credentials, runtimes, caches, and unrelated projects. Import is
path-safe, schema-versioned, verified before activation, and never overwrites
an existing project silently. Project archives are not encrypted and therefore
show a commercial-data warning before export.

## Canonical data model

The core entities are:

- **Project:** identity, language, status, revisions, settings, and source set.
- **SourceDocument:** immutable file metadata, digest, detected format,
  extraction status, and revision relationship.
- **SourceItem:** exact raw and displayed source fields plus file, sheet, row,
  page, or image-region provenance. Keeping both forms prevents parsing or
  formatting normalization from silently changing what the engineer saw.
- **PackagePlan:** AI-generated set of packages, rationale, quality review, and
  version.
- **PackageAssignment:** one source item to one owning package, including
  confidence, explanation, and decision provenance.
- **RuleMemory:** an approved matching rule scoped to one project or all
  projects.
- **MaterialRecipe:** versioned decomposition, inputs, formulas, units,
  assumptions, evidence, and approval state.
- **DerivedMaterialLine:** source item and recipe lineage, material identity,
  net quantity, waste, gross quantity, purchase unit, and procurement
  quantity.
- **Decision:** gate, alternatives, recommendation, user choice, scope, and
  timestamp.
- **AgentRun:** provider-neutral task state, normalized events, checkpoints,
  and outcome.
- **Artifact:** file identity, revision, variant, digest, and lineage manifest.

## Multi-source ingestion and revision handling

All BOQ sources in a project contribute to one project master and one set of
specialist package workbooks.

Tawreed fingerprints sources and detects probable overlap, duplicates, and
revisions. It never assumes that similar files are additive or replacements.
When overlap is detected, the engineer selects one of these relationships:

- addition;
- replacement; or
- revision.

The decision is saved with the project. Replacement and revision behavior must
preserve prior source metadata and published outputs for auditability.

## AI Package Architecture

Tawreed does not start from a fixed package taxonomy. The AI acts as a Package
Architect and generates the package structure dynamically for each project.

The optimization objective is a market-ready balance:

- clear specialist scope;
- alignment with supplier or subcontractor markets;
- practical package size;
- semantic and construction-method coherence; and
- no unnecessary fragmentation.

The AI may use approved project and global rules as memory, but memory does not
limit its ability to propose a new project-specific structure.

Each source item has exactly one owning package for totals and publication. If
an item plausibly belongs to multiple packages, Tawreed shows the candidate
packages and rationale, asks for a decision according to the operating mode,
and then offers three memory scopes:

- this item only;
- this project — default; or
- all future projects — explicit opt-in.

Rules are inspectable, editable, removable, versioned, and conflict-aware. A
stored rule does not override a materially different context silently.

## Commercial Data Gate

When Tawreed detects rates, amounts, budgets, cost codes, markups, or internal
commercial notes, it pauses once at the output-set level and describes the
detected fields.

The engineer chooses:

1. **Internal output:** retain commercial data;
2. **External pricing output:** remove internal values while retaining empty
   pricing fields where appropriate; or
3. **Internal and external outputs — recommended:** generate both sets.

The source ledger remains unchanged. Derived files are named and marked
clearly, including `INTERNAL - NOT FOR ISSUE` and `FOR PRICING`. The gate is
mandatory in every operating mode.

## AI Material Takeoff

The user-facing capability name is **AI Material Takeoff (MTO)**. Its primary
export is a **Material Requirements Schedule**. It does not become a
procurement schedule until dates, lead times, orders, and delivery status are
added, which are outside this design.

### Material categories

The MTO distinguishes:

- primary materials;
- constituent materials;
- ancillary materials and accessories;
- consumables; and
- waste allowance.

### Agentic recipe generation

The AI acts as a Material Engineer. For each relevant BOQ item it:

1. interprets the item description and source unit;
2. identifies required materials and accessories;
3. generates or selects a Material Recipe;
4. identifies missing engineering parameters;
5. proposes explicit assumptions when necessary;
6. calls deterministic calculation and unit tools;
7. checks dimensional consistency and coverage; and
8. stores an approved recipe for future use.

The recipe library is memory and evidence for the AI, not a fixed engine that
replaces AI judgment.

### Engineering Assumption Gate

Tawreed must not silently invent missing dimensions, mix ratios, joint sizes,
material grades, waste percentages, packaging sizes, or similar engineering
parameters. It proposes a value, formula, impact, and rationale and requests
approval before first use. Approved assumptions can be scoped to the item,
project, or global recipe memory.

### Quantity presentation

Every derived material line exposes:

- net engineering quantity;
- waste percentage and waste quantity;
- gross requirement;
- procurement unit;
- package or container size where applicable;
- rounding rule; and
- final procurement quantity.

Material consolidation is semantic. Tawreed combines materials only when name,
specification, grade, unit, and other identity-defining attributes are
compatible. Potential matches are reviewed before consolidation. Every total
retains lineage back to each source item and recipe, and consolidation must not
double count quantities.

## External research and provider consent

Tawreed may perform generic research that contains no project data. If a query
requires a source description, quantity, project name, or other project
context, the External Research Gate shows:

- the exact minimum data to be shared;
- the destination provider or service;
- the purpose; and
- the expected result.

No operating mode bypasses this gate. Approval is also required before the
first provider fallback that would disclose project data to a new provider.

## Processing flow

```text
Create or open project
  -> add one or more BOQs
  -> decode, OCR, and build immutable source ledger
  -> resolve overlap and revision relationships
  -> generate and self-review Package Plan
  -> resolve ambiguous assignments and save approved rules
  -> evaluate Commercial Data Gate
  -> generate and validate Material Recipes
  -> resolve Engineering Assumption Gate
  -> calculate and consolidate materials
  -> preview selected artifacts according to operating mode
  -> publish complete revision atomically
  -> record audit trail and resumable checkpoint
```

Tasks continue while the app is open or minimized. Closing the application
stops local work safely. The next launch resumes from the last valid
checkpoint. The initial release does not install a background operating-system
service that continues after the application exits.

## User experience

The selected shell is **Adaptive Agent Workspace**.

### First run

The first-run flow is deliberately nontechnical:

1. Preparing Tawreed for First Use;
2. runtime verification and health check;
3. language and output preferences;
4. AI Connections Center; and
5. create or open a project.

Technical component names are hidden behind a collapsed details affordance.

### Project home

The project launcher exposes:

- create project;
- open recent project;
- import `.tawreed-project.zip`;
- incomplete task state; and
- connection health.

### Workspace composition

The top bar shows project name, operating mode, agent state, and connections.
A compact Agent Rail expands during conversation, approvals, warnings, or when
the user opens the activity history. The Live Workspace keeps most horizontal
space for large tables and provides these primary views:

- Sources;
- Packages;
- Material Takeoff;
- Decisions; and
- Outputs.

The engineer can merge, split, rename, and reassign packages through direct
manipulation or natural-language instructions.

Decision Cards show the question, reason, affected data, Tawreed's
recommendation, and impact of each choice. The UI does not expose SDK, model,
or runtime jargon outside advanced settings.

### Visual system

The selected direction is **Precision Neutral**:

- warm graphite and off-white foundations;
- restrained brass for attention and active state;
- no decorative gradients or dashboard clutter;
- Inter for Latin text and IBM Plex Sans Arabic for Arabic, bundled locally;
- RTL and LTR parity;
- keyboard operation and accessible focus states;
- scalable text; and
- system light and dark theme support.

## Reliability and failure handling

### Error classes

- **Transient:** provider timeout, network loss, or rate limit. Retry with
  bounded backoff, then prepare provider fallback.
- **Recoverable:** OCR failure, unsupported encoding, incomplete extraction, or
  output file lock. Preserve progress and request the smallest corrective
  action.
- **Decision required:** overlap, ambiguity, commercial data, external sharing,
  or engineering assumption. Pause at a gate.
- **Fatal:** invalid runtime signature, corrupted project store, unsafe archive,
  or unrecoverable publication failure. Stop safely and preserve source data
  and the last valid checkpoint.

### Invariants

- All agent changes occur in a reversible draft before publication.
- Cancellation preserves completed checkpoints.
- Publication is atomic: the whole revision is visible or none of it is.
- Every published artifact has a new revision and digest.
- No source item disappears silently.
- No source item contributes to more than one owning package total.
- No material quantity lacks source and recipe lineage.
- Logs and diagnostics redact credentials.

If no AI provider is available, the project and sources remain inspectable, but
Tawreed does not pretend to perform agentic package or MTO analysis.

## Security and trust boundaries

Source files are untrusted data. Text found in a BOQ, PDF, image, cell comment,
or formula must never be treated as system or developer instructions. Agent
prompts and tools separate document content from executable instructions and
are tested against prompt injection.

Additional controls include:

- strict project-scoped filesystem access;
- path traversal and archive extraction defenses;
- host allowlists for bootstrap and provider traffic;
- signed runtime manifests and assets;
- minimal external-data disclosure;
- provider-specific payload limits;
- atomic staging directories;
- redaction of credentials and sensitive diagnostics; and
- user-visible audit events for external access and provider fallback.

## Verification strategy

### Unit and property tests

Cover normalization, provenance, hashing, unit conversion, formula evaluation,
waste, procurement rounding, semantic material identity, rule conflict
handling, gate decisions, and state reduction.

Property tests protect these invariants:

- no source mutation;
- no missing or double-counted owning assignment;
- dimensional consistency of calculations;
- sum of consolidated quantities equals the sum of contributing lines; and
- safe round-trip serialization for text-first stores.

### Golden document tests

Use representative, non-customer fixtures for Excel, legacy spreadsheets,
searchable PDF, scanned PDF, Arabic, English, mixed language, and image-based
BOQs. Golden outputs verify item extraction, source lineage, workbook content,
and formula-free values where source fidelity requires them.

### Provider contract tests and agent evals

Every provider bridge runs the same recorded contract suite for session
continuity, streaming, cancellation, normalized error handling, and tool calls.
Agent evals use engineer-reviewed BOQs to assess package coherence, ambiguity
detection, recipe completeness, and faithful escalation. Provider-specific
behavior must not change the Tawreed domain contract.

### Integration and end-to-end tests

Test:

- first-run bootstrap and interrupted resume;
- invalid signatures and hashes;
- runtime health-check rollback;
- multi-document revision decisions;
- all operating modes and hard gates;
- provider fallback consent;
- complete master and standalone workbook generation;
- internal and for-pricing variants;
- consolidated and package-level MTO;
- project export and import; and
- pause-on-exit and resume-on-launch.

Generated workbooks must be opened and inspected by a compatible spreadsheet
reader as part of automated validation.

### UX, performance, and cross-platform tests

Test RTL/LTR, keyboard navigation, text scaling, screen-reader semantics, and
system themes. Representative large BOQs protect acceptable memory usage,
streaming responsiveness, OCR cancellation, and table performance. Windows
x64 is the first packaging gate; macOS and Linux use the same project fixtures
and contract suites when their distributions are introduced.

## Success criteria

The redesign is successful only when:

- a user starts from one visible application artifact and installs no manual
  dependencies;
- the complete runtime is verified and managed under `~/.tawreed`;
- users complete the main workflow without understanding SDKs or models;
- every source value remains unchanged;
- every active source item is assigned once or presented as an unresolved
  decision;
- every output item and material total is traceable to source;
- every derived quantity exposes recipe, assumptions, and calculation;
- no project data is shared without the applicable approval;
- no partial output revision is published;
- interrupted work resumes from a verified checkpoint; and
- provider changes do not change the product's domain behavior.

## Delivery decomposition

This system is too large for one implementation plan. Delivery is split into
four independently verifiable subprojects that share this architecture.

### 1. Platform foundation

- portable launcher and signed runtime bootstrap;
- text-first project store;
- Tauri shell and Adaptive Agent Workspace foundation;
- agent kernel, checkpointing, and local IPC;
- Codex SDK bridge; and
- AI Connections Center.

### 2. AI package preparation

- multi-source BOQ ingestion;
- overlap and revision resolution;
- dynamic package generation;
- assignments, rules memory, and commercial gate; and
- master and standalone workbook publication.

### 3. AI Material Takeoff

- AI material decomposition;
- recipes, assumptions, and calculations;
- waste and procurement quantities;
- semantic consolidation; and
- consolidated and package-level MTO outputs.

### 4. Provider and platform expansion

- Claude and Gemini bridges;
- automatic routing and controlled failover;
- project import/export hardening;
- macOS and Linux packaging; and
- production update and rollback hardening.

Each subproject receives its own implementation plan and release gate. Later
subprojects may begin only when the contracts they depend on are stable.
